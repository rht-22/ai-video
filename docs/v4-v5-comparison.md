## 0. 한 줄 결론

두 문서는 **다른 문제를 푼다.**

- **v4** — "어떻게 더 좋은 편성을 *고르나*". 후보 다중생성 → 결정적 깔때기 → offset 멀티파트
  시각 플래그 → 코드 순위 top-3 → 승자만 살붙이기. Gemini API 직접 실측 10종과 적대 검수
  24건이 근거다.
- **v5** — "새 트리를 지어도 사고 대응이 *사라지지 않게* 어떻게 짓나". v3 포크 · 바깥 계약 표
  (현지화·편집실·로더) · v1 모놀리스 함수 추출 · 필드 단위 대조 도구가 골자다. 3시간 실물
  업로드와 Stage 1 fps 자동화 **코드 출하**(e8aadda)가 근거다.

겹치는 실측(토큰 산식 · media_resolution · 초벌 렌더 결함)은 **독립적으로 같은 답**을 냈다.
골격이 실제로 충돌하는 지점은 하나(시간 정본 — span id 강제 vs 절대초+검증)뿐이고, 나머지
차이는 초점 차이다. **v5 골격 + v4 의 proxy:compose 내부**로 합치면 하나가 된다(§6).

## 3. 갈리는 것 — 충돌인가, 관점 차이인가

### 3-1 시간 정본 (유일한 골격 충돌)

- **v4**: 운영자 결정 "격자 단계 없음". 단 §5 가 못박듯 "재료 없음"은 아니다 — 전사 단어·장면전환·
  무음은 남긴다. LLM 이 절대초를 낸다(후보 조각·offset). 방어는 게이트다: 7단계 소스범위 하드 필터 ·
  전사 대조 · 경계 벨트(`endOffset` 이 소스를 넘어도 조용히 클램프되는 것 대비) · 승자 비대칭 스냅
  (start 앞 ≤2.0/뒤 ≤0.5 · end 뒤 ≤2.0 — 대칭 스냅은 리액션 꼬리를 자른다는 E20-B1 규율).
- **v5**: 격자도 별도 단계가 아니다 — `transcribe` 안 산출이다. 즉 "단계 없음" 결정과 충돌하지
  않는다. 다른 것은 **하류가 시각을 말하느냐 span id 를 말하느냐**다. v5 는 모델이 시각을 아예
  출력하지 않게 하고(Stage 2 실측 1,232/1,232 정합) 검증 단계가 눈금 밖 컷을 차단한다.
- **판정**: 관점 차이지만 강도가 다르다. v4 는 933 문제(LLM 시각 환각)를 *게이트로 잡고*, v5 는
  *구조로 없앤다*. v4 의 후보가 offset 파트로 표현되므로 후보 조각 경계를 span 경계로 강제하는
  것은 추가 비용 0 — v4 안에 v5 방식을 넣는 데 장애가 없다. 반대로 v4 가 짚은 "대칭 스냅의
  꼬리 절단"은 v5 의 무성 span 재단(장면전환·무음 경계)에도 같은 검토가 필요하다.

### 3-2 토큰 산식 — 둘 다 맞고, 함정이 둘이다

- v4: `usageMetadata` 기준 **프레임 66 · 오디오 25**. `countTokens` 는 71/32 로 다르게 세고
  **멀티파트(offset)는 3.8배 과소** 계산한다(3파트 142 vs 실과금 546).
- v5: `count_tokens` 기준 **71 · 32**. 실호출은 12~14% 낮은데 원인을 `media_processing`
  STATIC/AGENTIC 차이 *가설*로 남겼다. 그리고 **400 상한 초과는 count_tokens 값으로 난다** —
  3시간 fps 1.0: count 1,112,401 → 400. usage 산식이면 982,800 으로 상한 안이다.
- **교차 검증**: 12~14% 차이는 상수 차이로 완전히 설명된다. 60초·1fps: count 60×(71+32) = 6,180,
  usage 60×(66+25) = 5,460 → 88.3%. 가설이 필요 없다.
- **합성**: 서로 다른 함정을 각각 잡았다.
  1. 단일 파트 **상한 판정** → 71/32 (v5). v4 의 85% 예산선은 66/25 로 계산돼 있어 count 단위로는
     더 높다. 90분·fps 2: usage 847,800(80.9%) 이지만 count 939,600(**89.6%**). 상한은 안 넘지만
     프롬프트·전사 여유가 109k 로 준다.
  2. 멀티파트 **과금·예산** → `usageMetadata` (v4). `countTokens` 로 재면 컨텍스트 초과를 못 잡는다.
  ⚠ CLAUDE.md 「V3 표본 fps·해상도 계약」은 1번만 싣고 있다 — 2번(멀티파트 함정·66/25 과금)이 없다.

환산 비율(usage/count)은 fps 에 따라 0.883(1fps)~0.919(6fps)다. 67분(4,020s) 기준 통일 표:

| 설계 | 입력 토큰(usage) | 비고 |
|---|---|---|
| v5 2켜(상세 생략) | ≈0.45M | 품질 미검증 기준선 |
| **v4** | ≈0.96~1.05M | exception 프로브 150~230k 포함 · 첫 30편 fps1 shadow +0.37M |
| v5 지연 상세(4/10·5fps) | ≈1.05M | refine 별도 0~0.56M |
| v3 현행 | ≈1.29M | v4 §6 계산 |
| v5 전량 상세(3fps) | ≈1.43M | refine 별도 0~0.56M — v3 현행에 텍스트 프롬프트 80k 가 더해진 값 |

⚠ 입력만이다. 출력·thinking 단가는 입력의 5배(v4 §6) — v5 는 이 항을 비용 표에 넣지 않았다.

### 3-3 훑기 fps — 모순이 아니라 구조의 귀결

- v4: 기본 **2**(60분 565k, 상한 3), 규칙 `min(파일fps, 24, 예산 역산)` — "올릴 수 있는 만큼".
  근거는 프레임이 실제로 더 전달된다는 메커니즘 실측(12/24/60)이고, 정당화는 "후보를 갈라 뽑을
  재료"다. 편성 품질 향상은 미검증 → 첫 30편 fps 1 shadow 관측.
- v5: 기본 **1.0** 고정, 161분까지 회귀 0, 넘치면 0.05 계단 내림, 하한 0.5 = 1/`SNAP_TOLERANCE_SEC`.
  **이미 코드 출하**(`seq_analyze.resolve_scan_fps`, 테스트 37건). 상세 켜 3fps 도 "근거 없음" →
  M9 A/B.
- **판정**: v4 는 청크 상세를 없앴으므로 훑기 해상도가 후보 품질의 상한이 되고, 그래서 fps 를
  올려야 한다. v5 는 상세 켜가 조밀한 재료를 주므로 훑기는 1 로 충분하다. 합치면(지연 상세 유지)
  fps 1 로 시작하는 것이 자연스럽고, v4 의 shadow 관측을 **방향만 뒤집어**(fps 2 shadow) 걸면 된다.
  "fps 상향이 편성 품질을 올린다는 근거는 아직 0"이라는 데 두 문서가 일치한다.

### 3-4 v3 와의 관계 — v5 가 v4 의 전제를 정면 반박한다

  끝난다", `score_story` 확장, refine 방식 분리. 즉 "공유 모듈 재사용" 전제다.
- v5 §5: **바로 그 방식으로 지은 v3** 가 v1 모놀리스를 한 줄도 import 하지 않았고, E10·E12·E14·
  E18-2·E19·E20·E21 대응을 하나도 승계하지 못했으며, 현지화가 깨져 있다.
- **코드 확인**(§5): 사실이다. `app/localize/apply.py:182~186` 은 `story["variants"][*]["title_text"]`
  와 `story["title_text"]` 를 쓰는데 v3 story 는 `title.{line1,line2}`(`story.py:246`)뿐이다.
  `rerender.py:142` 는 v1 `app.cli create_shorts --from-step render` 를 서브프로세스로 부른다.
- **귀결**: v4 문서에 현지화가 **0회** 등장한다. v4 를 문서대로 지으면 v3 와 같은 자리에서 깨진다.

### 3-5 청크 상세 vs 후보 다중생성 — 서로의 미결이 서로의 답이다

- v4: Stage 2 청크 정밀 분석을 **삭제**했고 "등가성 미검증"(§10)으로 남겼다. 대신 후보 12~16 +
  깔때기 + 시각 플래그로 선택 품질을 확보한다. v3 골든 대조에서 모델이 사람과 *다른 스토리*를 고른
  문제(M3 실측 matched 2/14)에 대한 직접 답이다.
- v5: 상세 켜를 유지하되 "전량 필수 근거 없음" → 2켜 기준선 → **④ 주도 지연 상세**(④가 고른 후보
  span 근방만 + 인접 확장) 순으로 A/B. 스토리 선택 자체는 "변수"로 남겼다 — 기제가 없다.
- **합성**: v5 의 "④가 고르는 후보" = v4 의 깔때기 top-3. v4 의 6~9단계가 v5 ③의 트리거를 주고,
  v5 의 ③이 v4 의 "후보 품질 상한 = 훑기 해상도" 문제를 top-3 근방 한정으로 완화한다.
