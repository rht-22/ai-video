## 0. 왜 기존 트리를 고치지 않고 새로 짓는가

**한 줄: 기존 세 트리는 전부 "클립이 마스터"이고, 두 문서는 "오디오 행이 마스터"다.**

문서 ① 제1원칙이 명시한다 — *"내레이션 오디오의 길이(Duration)가 '주(Master)'가 되고,
비디오 편집은 그 길이에 맞춰야 한다."* 제2원칙은 그 길이를 **짧은 컷 여러 개로 쌓아서**
채우라고 한다(슬로우 모션 금지).

우리 v1·v3·v4 는 정확히 반대다:

1. 먼저 클립(구간)을 고르고,
2. 그 클립 위에 내레이션 cue 를 **얹을 자리를 찾는다**(`_resolve_cue_anchors`·
   `plan_narration_slots`·`snap_cues_to_dialogue_gaps`).
3. cue 가 창을 넘치면 **문장을 줄이거나 오디오를 자른다**(`synthesize_tts_with_fit` ·
   L3t `_trim_to_window`).

즉 **오디오가 비디오에 종속**이다. 문서가 요구하는 것의 정확한 역이다.

이 반전 때문에 부분 이식이 실제로 막힌 이력이 있다 — **V3-M15 가 컷 스태킹을 시도했다가
`verify_edit_plan` 에 82.35% 로 거절당했다**(클립 경계는 전부 격자 span 경계여야 한다).
`docs/v4/tikitaka-fit.md` §2-4 가 "다섯 묶음 중 가장 큰 작업"으로 남겨 둔 그 항목이다.

⇒ 스태킹·모드 [A]·비선형은 각각이 아니라 **한 뿌리(오디오 우선 타임라인)의 세 얼굴**이다.
뿌리를 바꾸는 것은 기존 트리 안에서 additive 로 못 한다. 새 트리가 맞다.

**⚠ 다만 백지가 아니다.** 격자(`app/modules/grid/`)·전사·프록시·Gemini 클라이언트·
렌더러·TTS 는 그대로 쓴다. 새로 쓰는 것은 **편성 표현과 시간 확정 규칙**이다.

## 1. 정본 자료구조 — 편집 테이블 (`edit_table.json`)

문서 ①의 출력 포맷(마스터 편집 테이블)을 **사람이 읽는 산출물이 아니라 파이프라인의 정본
문서**로 승격한다. 이후 모든 단계가 이 표를 읽고 쓴다.

```jsonc
{
  "schema": "v14_edit_table/v1",
  "strategy": {"no": 3, "name": "감정 폭발형"},
  "title": "…",                       // ② 출력 포맷의 어그로 제목
  "structure": "⑤하이라이트 → ②리액션 → ①발단",   // ② 재배치 구조
  "rows": [
    {
      "seq": 1,
      "mode": "N",                    // N 내레이션 · S 대사 · A 액션/앰비언스
      "audio": {
        "kind": "narration",
        "text": "승일이 결국 참지 못하고 폭발합니다.",
        "voice": "ko_female", "speed": "normal"
      },
      "dur_sec": 4.0,                 // ★ 이 행의 길이 — 오디오가 정한다
      "dur_basis": "estimate",        // estimate | synthesized | source
      "cuts": [                       // ★ 그 길이를 채우는 컷 스택 (제2원칙)
        {"span_id": "s0412", "start_sec": 671.35, "end_sec": 673.35,
         "note": "승일 물 마심", "src": "00:11.200"},
        {"span_id": "s0733", "start_sec": 1130.90, "end_sec": 1132.90,
         "note": "승일 고개 숙임", "src": "00:53.000"}
      ],
      "effect_subs": [                // ④ 예능형 효과자막
        {"text": "[동공지진 5.0]", "at_sec": 0.8, "dur_sec": 1.2, "kind": "emotion"}
      ]
    }
  ]
}
```

### 이 모양이 계약인 이유

- **행(row) 하나 = 문서 ①의 테이블 한 줄.** 사람이 읽는 마크다운 표는 이 JSON 의
  결정적 렌더링일 뿐이다(§7 `edit_table.md`). 문서를 "충실히 이행"한다는 말의 기계적 정의.
- **`dur_sec` 이 `cuts` 를 지배한다.** 검증기가 `sum(cuts) == dur_sec`(±0.05)을 강제한다.
  오디오가 마스터라는 원칙이 자료구조 불변식으로 박힌다.
- **`span_id` 와 `start/end` 가 함께 있다** — 문서 ①의 삼위일체(소스 ID + 타임코드 + 내용).
  `span_id` 는 격자 눈금이라 코드가 검증할 수 있고, `note` 가 장면 내용, `src` 가 사람이
  읽는 `MM:SS.ms` 다. 셋 중 하나라도 없으면 검증기가 그 행을 거절한다(제0-1원칙 무관용).
- **모드가 오디오 라우팅을 결정한다** — 렌더 어댑터가 이 한 글자로 원음/내레이션/뮤트를
  정한다(§6 표). 문서 ①의 제3원칙이 그대로 코드 분기가 된다.

## 2. 단계 구성

```
0 init → 1 probe → 2 transcribe+grid → 3 ◉scan → 3b ◉refine → 4 ◉detail

```
◉ = Gemini 가 **영상을 보는** 호출. 그 외는 텍스트 온리이거나 LLM 0콜.

단계 표는 `app/v14/steps.py` 한 곳(v4 규율 — `should_run` 은 순번 비교 하나).

### 2-1. 단계 4 detail — 모드 C 가 요구하는 재료

문서 ② 모드 C: *"전체 스토리(기승전결)를 완벽히 이해해야 한다 … 시각적 상황(액션, 표정),
인물의 숨겨진 심리, 세계관의 배경 설명을 내레이션으로 꽉 채워 넣고."*

v3 `chunk_analyze` 가 이미 span 별 {장면·인물·중요도·들은 대사}를 낸다. 모드 C 를 위해
**두 칸을 더 요구**한다(응답 스키마 확장 — 기존 키는 안 건드린다):

- `psych` — 그 span 에서 인물이 감추고 있는 것/속내 한 줄. 내레이션의 재료다.
- `sound` — 대사가 아닌 소리의 성격(`sigh`·`impact`·`laugh`·`silence`·`none`).
  **모드 [A] 의 유일한 재료**다.

⚠ `docs/v4/tikitaka-fit.md` §2-3 의 실측: 소리 사건을 **에너지로만** 검출하면
"대사 없이 소리가 큰 구간"이 나오지 "타격음"이 나오지 않는다(신병4 33분 29건 중 저역
충격음 1건). `grid/sound_events.py` 가 **후보를 좁히고**, 성격 판정은 이 단계에서
**영상을 보는 모델**이 한다. 이것이 이번 설계가 §2-3 을 넘어서는 지점이다.

### 2-2. 단계 5 rebuild — 10전략, 그리고 겹침 금지

문서 ② 모드 C 는 *"10가지 리빌딩 포맷에서 **겹치는 구간이 없도록** 전체 스토리에서
중복되지 않는 하이라이트를 추출한다"* 고 명시한다.

⚠ 이는 `docs/v4/tikitaka-fit.md` §2-2 가 적은 "10전략 × 같은 소재는 IoU dedup 과 정면
충돌"과 **반대 방향의 요구**다. 모드 C 에서 10전략은 같은 구간의 변형이 아니라 **한 회차를
10편으로 나눠 덮는 것**이다. 즉 dedup 을 끄는 것이 아니라 **전략 간 dedup 을 켜는 것**이
문서 충실이다. 채널 운영으로도 이쪽이 말이 된다(한 회차 → 10편 발행).

구현:

- 호출은 **전략당 1회**(총 10회). 한 응답에 10편을 담으면 출력 예산(thinking + 출력이
  65,536 공유)에서 잘린다 — v4 실측 1건 관측.
- 각 호출 프롬프트에 **이미 다른 전략이 쓴 span id 목록**을 실어 배제시키고, 코드가 사후에
  다시 검증한다(모델의 자발적 준수를 믿지 않는다).
- 전략 순서는 문서 ② 2단계의 1~10 고정. 재료 고갈로 뒤쪽 전략이 굶으면 **그 전략만 탈락**
  시키고 사유를 남긴다(편 전체 실패 아님).
- **모델은 시각을 출력하지 않는다** — span id 와 sound event id 로만 말한다. v3 Stage 2
  실측 1,232/1,232 정합의 근거를 그대로 승계한다(933 방어).

### 2-3. 단계 6 timefix — 이 파이프라인의 심장

편집 테이블 초안(span id 뭉치)을 **절대 시간이 박힌 컷 스택**으로 바꾼다. LLM 0콜 · 순수 함수.

```
행마다:
  1) dur_sec 확정
       모드 N → NARRATION_PAD_SEC(0.2) + 공백제외자수 / NARRATION_CPS(5.0)
       모드 S → 인용 대사 span 들의 실제 길이 합
       모드 A → 소리 사건의 실제 길이
  2) 그 길이를 컷 스택으로 채운다 (제2원칙)
  3) 각 컷에 ±0.1초 안전 마진 (제0-2원칙)
```

**① `dur_sec` 산식은 실측본이다.** `NARRATION_PAD_SEC + 자수/NARRATION_CPS` 는
`docs/v4/tikitaka-fit.md` §1 의 ElevenLabs 실합성 12건(N=12, RMSE 0.095초)에서 나왔고
이미 `app/v3/story.py:93` 에 상수로 있다. 문서 ①의 "4글자당 1초"(= 4.0 cps)는 **우리
백엔드에서는 과대**다 — 실측 5.17 cps. **문서의 숫자가 아니라 문서의 원칙(물리 시간을
먼저 계산한다)을 이행하고, 숫자는 우리 실측을 쓴다.** 이 갈림은 §5-3 에 기록.

**② 스태킹이 격자 벨트에 안 막히는 방법 — M15 가 놓친 것.**

M15 는 *한 span 을 내레이션 창 끝에서 쪼개려* 했고 그래서 막혔다. 이번 설계는 쪼개지 않는다:

> **스태킹 = 짧은 span 여러 개를 소스 여기저기서 골라 잇는 것.**
> 4초 창은 1.3초짜리 span 3개로 채운다. 클립 경계는 전부 격자 눈금이므로 벨트를 그대로 통과한다.

다만 1~2초짜리 눈금이 충분치 않을 수 있다(유성 span 은 문장 단위, 무성은 최대 6초).
그래서 **눈금 집합을 한 겹 넓힌다**:

```
클립 경계 허용 집합 = span 경계 ∪ 장면 전환점 ∪ {0, 러닝타임}
```

장면 전환점은 `grid/scenecut.py` 가 **ffmpeg 이 픽셀에서 잰 값**이다 — LLM 환각이 아니고
결정적이다. 벨트를 **완화하는 것이 아니라 눈금을 확장**하는 것이고, 컷 전환을 실제 장면
전환에 맞추므로 화면상으로도 옳다. 이것이 M15 우회의 정답이다.

**③ ±0.1초 안전 마진**(문서 ① 제0-2원칙 · 1단계) — 컷 경계에서 안쪽으로 100ms 씩 물린다.
⚠ 기존 E20-B1 비대칭 스냅 규율(리액션 꼬리를 자르지 마라)과는 **다른 층**이다. 안전 마진은
경계 글리치 방지(안쪽으로 좁힘), 비대칭 스냅은 편성 의도 보존(바깥으로 넓힘). 상수
`SAFE_MARGIN_SEC = 0.1` 하나로 열고 닫으며, 0.4초 미만 컷에는 **적용하지 않는다**(렌더의
0.2초 미만 컷 드롭 임계에 걸려 컷이 통째로 증발한다 — 실사고 이력 있음).

**④ 컷이 모자라면.** 문서는 슬로우 모션을 금지한다. 우리도 슬로우가 없다. 후보 span 이
고갈되면 순서대로: ⓐ 인접 span 으로 확장 → ⓑ 같은 인물의 다른 리액션 span 재사용(같은
전략 안 재사용 1회까지) → ⓒ **내레이션 문구를 줄인다**(Flash 축약 — 오디오가 마스터라는
원칙의 마지막 후퇴선) → ⓓ 그 행 탈락 + 기록. 조용한 늘이기·조용한 드롭 없음.

### 2-4. 단계 7 verify — 문서 ①의 최종 검수를 코드로

문서 ①이 요구하는 "강제 재수행"을 **차단 게이트**로 옮긴다(§5-2 참조 — 처음부터 재수행은
채택하지 않는다).

| 검사 | 판정 |
|---|---|
| 모든 행에 `span_id`+타임코드+`note` 삼위일체 | **차단** (제0-1원칙) |
| `sum(cuts) == dur_sec` ±0.05 | **차단** (제1원칙) |
| 컷 경계가 허용 눈금 집합에 있음 | **차단** (933 방어) |
| 컷이 소스 범위 안 | **차단** (`clips_beyond_source` 규율) |
| 모드 S 인용 대사 ↔ 전사 편집거리 ≤0.35 | **차단** (환각) |
| 인트로·예고 구간 유입 | **차단** (`stage1.json` exception) |
| 전략 간 구간 겹침 | **경고 + 지표** (모드 C 요구 · 편을 죽이진 않는다) |
| 0.4초 미만 컷 | 경고 |
| 첫 행이 모드 N 이 아니고 3초 초과 | 경고 (② 마의 3초 룰) |

## 3. Gemini 호출 설계

## 4. 렌더 어댑터 — 모드 → 화면·소리

`app/v14/render_adapter.py`. 편집 테이블 한 장 → `RenderInputs` 하나.

| 모드 | 원본 오디오 | 내레이션 | 자막 | 렌더 배선 |
|---|---|---|---|---|
| **N** | **뮤트** | TTS cue 재생 | TTS 자막(내레이션 문구) | `muted_windows` + `tts_cue_files` |
| **S** | **원음** | 없음 | 대사 자막(전사 정본) | `subtitle_path` |
| **A** | **원음** | 없음 | 없음(또는 효과자막만) | 아무것도 안 얹음 |

- 세 모드 전부 **기존 `renderer.render_short` 로 표현 가능**하다 — `muted_windows` 는
  이미 additive 로 있고(v1 회귀 0 규약), cue·자막·`image_overlays`·`sfx_audio` 도 있다.
  **렌더러는 한 줄도 안 고친다**는 것이 M1 합격 조건이다.
- 효과자막(② 제4원칙)은 v1 E15 어휘 `texts[]` 로 간다 — `build_texts_ass` + 밴드 클램프
  (E18-2) + 얼굴 회피(E19-4)가 이미 있다. ⚠ 그 배선은 **v1 에만** 있으므로 v14 가
  호출부를 새로 붙인다(`docs/v4/tikitaka-fit.md` §2-5 가 짚은 공백).
- ⚠ **연출/BGM 군은 1차 범위 밖**이다 — `[화면 흑백 전환]`·`[삐- 처리]`·`(BGM: …)` 은
  렌더 능력 자체가 없다. 1차는 **감정·상황/태클 군만** 낸다(라벨로 표현 가능). 문구를
  짓게 두고 렌더만 안 하면 "고쳤는데 왜 그대로지"가 된다 — 프롬프트에서 그 군을 **금지**한다.

## 5. 문서와 우리 현실이 갈리는 지점 (전부 명시적 결정)

### 5-1. Content ID 회피 — **제외**
문서 ②는 "오디오 핑거프린트 매칭 회피"를 목표로 적고 텍스트 일치율·키워드 변형률을
출력하라 한다. 우리는 **권리사 라이선스 콘텐츠**를 다루므로 회피가 목표가 아니고 목표여서도
안 된다. 게다가 우리 계약은 정반대다 — 인용 대사는 전사 그대로이고 편집거리 0.35 를 넘으면
환각으로 드롭한다. **비선형 재조립의 근거는 이탈률 하나만 남긴다.**
출력 포맷의 그 절은 **"전략 간 구간 중복도"** 지표로 대체한다(모드 C 가 요구하는 것).

### 5-2. "즉시 처음부터 다시 수행" — **재질의 ≤2 로 대체**
문서 ①은 불일치 1건이면 처음부터 재수행하라 한다. 우리는 반려 사유를 덧붙인 재질의 2회
후 그 **행/전략만** 탈락시킨다. 처음부터 돌면 비싼 상류(전사·격자·업로드)를 통째로 버리고,
실측에서 재질의가 실제로 구조 결함을 잡아냈다(v3 Stage 2 s1c0).

### 5-3. "한국어 4글자당 1초" — **실측 5.17 cps 를 쓴다**
문서의 4.0 cps 는 우리 TTS 백엔드에서 25% 과대 견적이다(§2-3 ①). 원칙은 이행하고 상수는
실측을 쓴다. 백엔드·목소리·속도를 바꾸면 다시 잰다.

### 5-4. 데이터 무결성 — **우리가 이미 더 엄격하다**
문서 ①의 삼위일체·근사치 금지는 우리 격자 계약이 이미 넘어선다. 문서가 요구하는
`MM:SS.ms` 표기는 **내부 정본이 아니라 출력 포맷**으로 이행한다(§7) — 내부는 초 단위
float + span id 이고, 사람이 보는 표에서 `MM:SS.ms` 로 찍는다.

### 5-5. 비선형 — **모델이 아니라 코드가 한다**
`docs/v4/tikitaka-fit.md` 실런: 프롬프트 절을 켜고 출력 예시까지 역순으로 바꿔도
**비선형 0/6**. 모델의 시간순 편집 사전확률은 프롬프트로 안 꺾인다.
⇒ v14 는 rebuild 에게 **전략 이름과 역할 슬롯**만 시키고(예: 전략1 = `[결말][발단][전개][위기]`),
**행 순서 배열은 timefix 가 코드로** 한다. 오판 3자리(`verify._conflicts`·`funnel.lead_in_sec`·
`bridge.snap_segments`)는 이미 고쳐져 있어 재배열이 안전하다.

```
outputs/<job>/
  run_log.json  grid.json  stage1.json  stage2.json
  tables/strategy_01.json … strategy_10.json     ← 정본
  verification.json
  shorts_01.mp4 … shorts_10.mp4
  edit_table_01.md … edit_table_10.md            ← 문서 ① 포맷 그대로
```

`edit_table_NN.md` 는 문서 ①의 표를 **그대로** 찍는다 — 열 6개, `<br>` 금지,
컷 구분은 `(1), (2)` 와 `/`, 타임코드 `MM:SS.ms`. 문서 ②의 머리말(제목·재배치 구조)과
꼬리말(바이럴 분석 — Content ID 절은 §5-1 대체본)도 함께. **결정적 렌더링**이므로
같은 테이블이면 바이트까지 같다(테스트 고정).

## 9. 열린 항목

1. **효과자막 밀도** — 문서는 "적극 삽입"이라 하지만 v1 하드캡은 텍스트 8개다. 모드 C
   롱폼 축약(60~120초)에서 몇 개가 적정인지 실측 없음.
2. **10편 발행 운영** — 같은 회차 10편을 실제로 다 발행할지, 상위 N 편만 발행할지는
   채널 운영 결정. 파이프라인은 10편을 만들고 **선택은 사람에게** 남긴다.
3. **모드 [A] 성격 판정 정확도** — 단계 4 의 `sound` 칸이 실제로 한숨·타격음을 구분하는지
   레이블 없음. M3 에서 표본 확보.
4. **길이 예산** — 모드 C 롱폼 축약의 목표 길이(현행 `MAX_DURATION_SEC` 120초)를 이
   포맷에 그대로 쓸지.
